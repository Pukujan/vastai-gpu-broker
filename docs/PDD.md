# Property-driven development plan

This plan defines externally observable properties before the runner implementation. Each property must have a test that can fail independently of the implementation's chosen structure. [SPEC.md](../SPEC.md) is the requirement authority; [SDD.md](SDD.md) defines the contracts and [TDD.md](TDD.md) defines the acceptance evidence.

## Properties

| ID | Property that must remain true | Observable failure |
|---|---|---|
| P01 | Missing exact-model research produces a concrete research action before any paid call. | A create request precedes resolved identity and source evidence. |
| P02 | Every decisive deployment claim has a retrievable source, provenance class, and matching model/runtime scope. | A fabricated field, unrelated model report, or generic VRAM estimate passes. |
| P03 | Unknown stays unknown; externally tested hardware is reported as tested, not as a proven minimum. | A contributor report becomes a publisher requirement or a universal fit claim. |
| P04 | The agent discovers the model's actual inference interface and dependencies. | An adapter is treated as standalone weights or a decision API as text generation. |
| P05 | Simultaneous model requests require simultaneous evidence or authorized validation, and readiness exercises the complete resident set and its declared concurrent workload. | Individual successes, partial readiness, or sequential model switching pass as simultaneous fit or acceptance. |
| P06 | Tightening a constraint cannot admit a previously rejected offer. | Lower caps or stricter resource limits increase eligibility. |
| P07 | Input ordering, irrelevant text, verification labels, and duplicate records do not alter the selected distinct offer. | A cheaper equally eligible unverified machine is silently excluded. |
| P08 | Comparison includes requested disk and network cost; no cost is counted twice. | Compute-only ranking selects an offer with higher known total task cost. |
| P09 | Every paid transition stays within explicit authorization and planned limits. | Missing/negative/nonfinite caps pass or a bid exceeds its cap. |
| P10 | Freshness and evidence identity are checked immediately before create. | A committed cache, changed recipe, or expired quote authorizes create. |
| P11 | Bidding terminates within attempt, time, bid, and spend limits. | Escalation loops forever or claims a higher bid guarantees startup. |
| P12 | One request ID and bound deployment/limits digest owns one coordinated operation: sequential mode has at most one unresolved lease; an explicitly authorized race has only its finite reserved contenders, with at most one create per attempt. | Duplicate callers, timeout, retry, or controller restart create a duplicate operation/attempt or an unreserved contender. |
| P13 | No instance access is returned before durable ownership and cleanup supervision. | An agent can use a lease with no recoverable instance ID/deadline. |
| P14 | Completion/failure/cancellation all converge on destruction and verification for every owned instance and separately billed volume, except resources explicitly retained until their bounded deletion deadline. | A stopped, paused, or delete-acknowledged resource is reported cleaned up, or a retained volume has no active cleanup obligation. |
| P15 | Restart reconciles the same request's outstanding attempts, instances, retained volumes and reservations before new work. | A crash leaves an orphan resource or loses reserved exposure while a replacement launches. |
| P16 | Inference success proves the requested artifacts and interface were used. | An empty ready port, dummy output, wrong checkpoint, or wrong schema passes. |
| P17 | Any uncertainty in cleanup remains a visible failure and retryable obligation. | API failure is translated into "no ongoing cost". |
| P18 | Credentials and evaluator secrets never enter public artifacts or logs. | Captured key/password/held-out payload is committed or echoed. |
| P19 | The reusable API and CLI share exactly the same policy transitions. | Importing the module bypasses CLI gates. |
| P20 | Checkpoints honestly state capability, checks, blockers, and next actions. | Target design or an unfinished paid challenge is labeled ready. |
| P21 | An unresolved artifact cannot rent without exact selection or scoped selection permission; exact artifact and authorized auto-selection proceed without another model question. | A vague base silently becomes a chosen quant, or valid exact/scoped authorization is ignored. |
| P22 | Model hosting idle/cold timers use actual authenticated model work and terminate at explicit limits. | Agent heartbeat/port polling prevents idle cleanup, or stop is reported as ending storage billing. |
| P23 | Ambiguous-model research returns a sourced candidate comparison and live per-candidate pricing statistics before confirmation. | A variant is silently picked or sample statistics/requirements are transferred across quants. |
| P24 | A resolved official base does not silently resolve an open quantization/format/provider artifact choice. | Community quant weights are selected as if "official base" authorized that artifact. |
| P25 | Exact repository/URL plus artifact confines research to that candidate and its dependencies. | A broad alternative menu or redundant model question delays a resolvable exact request. |
| P26 | Scoped selection authorization selects only permitted artifacts and preserves independent cost/evidence/lifecycle gates. | An authorized 4-bit choice prompts again, widens to another base/bit depth, or invents missing numeric caps. |
| P27 | Absence/ambiguity and retrieval failures yield distinct routes with a recorded alternatives-question decision. | Missing artifact silently becomes another model, or a transient fetch error is called artifact absence. |
| P28 | Resource estimates use exact sourced architecture/artifact/runtime/workload inputs and show known/unknown weight/cache/overhead terms. | Parameter-count rules of thumb or file size become an unsupported fit claim. |
| P29 | MoE total/resident weights remain distinct from active parameters and documented offloaded residency. | Active-per-token parameters are used as all resident weight memory. |
| P30 | Cache formulas follow the actual attention/recurrent architecture and context/concurrency/dtype/placement. | Dense full-attention KV rules silently apply to hybrid/MLA/recurrent caches or omit workload growth. |
| P31 | The current owner network policy checks both directions: less than $1/TB is preferred, $2/TB through $3/TB inclusive is expensive, and any direction above $3/TB is rejected; its source and unit basis are visible. | An old $10/TB rejection rule overrides the owner, exactly $1 is called preferred, exactly $3 is rejected, or a cheap direction hides an expensive one. |
| P32 | Transfer and storage conversions require scoped provider evidence; native per-GB, native per-TB, display conventions, byte divisors and month divisors remain distinct. | Guessed 1000/1024, GB/GiB, 730 hours/month, or conflicting fields become an exact cost or a passed rate gate. |
| P33 | A candidate's full phase/transfer/storage ledger binds exact allocations and counts each charge once, with estimates, authorized envelopes and observed charges separate. | Startup/download/benchmark, stopped retention, retries or cleanup disappear; `dph_total` receives its compute/storage components twice; unknown traffic becomes zero. |
| P34 | A retained artifact cache has measured reuse savings, pinned identity, host/attachment scope, a separate quoted cost and a bounded lifetime. | An absent/expired/wrong-revision cache reduces cost, a same-machine volume is treated as portable, or unknown reuse terms produce a numeric break-even claim. |
| P35 | Prepared local harness, GPU-host engine/loopback metrics, remote Tailscale metrics and task-checker results retain separate protocol and workload provenance. | WAN throughput becomes pure GPU performance, an unprepared paid harness loses unbudgeted time, or unknown PC/Linux/Mac specifications and local costs become assumed facts. |
| P36 | Application bytes, scoped transfer counters and provider-billed usage/charges are separate directional observations with interval, retries and limitations. | Tokens stand in for wire bytes, counter resets undercount traffic, or local counters are labelled exact provider billing. |
| P37 | Parallel bidding requires finite authorized contenders and atomic reservations covering aggregate instance/GPU/hourly/bid/time/storage/network/cleanup exposure before dispatch and escalation. | Per-machine caps authorize an uncapped race, concurrent starts exceed the envelope, or a bid-floor quote survives a higher bid. |
| P38 | Cross-computer identical requests attach to one shared fenced operation, while a changed deployment/limits digest requires replan; unclear creates reconcile their own attempt. | Independent PC/Linux/Mac journals duplicate a lease, changed inputs reuse authorization, or a lost response allocates a replacement contender. |
| P39 | Race winner selection requires complete simultaneous acceptance; losers and their separate volumes retain budget reservations and cleanup obligations until verified absent. | First SSH/running/one-model response wins, loser deletion acknowledgement releases exposure, or lingering volumes permit a single-contract/cleaned-up report. |
| P40 | The plan distinguishes GPU start urgency from inference-performance targets, honors the user's simultaneous or sequential model mode, and binds "run it" approval to the reviewed model set, quote, acquisition strategy, deadlines, and hard cost limits. | A vague speed preference becomes guessed limits, sequential loading passes simultaneous acceptance, a changed quote silently spends more, or the router substitutes a model the user did not choose. |
| P41 | The independent cleanup supervisor is running and durably armed before create; a completed benchmark result is persisted and delivered immediately, while cleanup verification arrives separately and may remain pending. | An install hang runs without a watchdog, benchmark results are withheld until deletion, or pending cleanup is presented as verified. |
| P42 | A lease has a recovery guardian outside the rented GPU host; supervisor heartbeat loss is detectable and leads to provider reconciliation, destroy retries, and an actionable alert. The product states that no controller can promise a hard spend cutoff if every control path or Vast itself is unavailable. | A same-host child process is presented as surviving host failure, a dead watchdog is silently accepted, the GPU receives the account API key for self-deletion, or the spend cap is represented as provider-enforced. |
| P43 | The planner enforces the user's per-run spend and lifetime limits independently of account balance. Vast's zero-credit behavior is documented only as provider behavior; the broker never waits for balance depletion as a cleanup trigger or calls it the lease fail-safe. | Balance depletion is the planned cleanup mechanism, or it is presented as an exact final-bill cap despite continued storage charges and grace/autobilling behavior. |
| P44 | The broker automatically starts verified destruction when the requested work completes, fails, is cancelled, or exceeds its authorized idle/deadline policy. The agent is not the sole cleanup owner: an independent guardian detects agent/controller/watchdog loss and destroys the lease, then verifies provider-side absence. | A human must remember to close a GPU, agent exit leaves a lease unmanaged, stop/pause is reported as deletion, or a destroy acknowledgement is called verified cleanup. |
| P45 | Before create, two cleanup paths in separate control-host failure domains acknowledge the fenced lease intent and deadline in a durable registry both can read. Each can reconcile and destroy only request-owned resources. A browser session or scheduled workflow alone cannot satisfy this gate. | The GPU starts with only the agent or same-host child process watching it, a guardian cannot read the lease after the initiating host dies, or loss of both paths is reported as guaranteed cleanup. |
| P46 | Completion, failure, cancellation, and deadline cleanup publish a durable, fenced `cleanup_requested` signal for the independent recovery workers. The signal starts cleanup promptly but never proves provider-side absence; only fresh complete instance and volume inventories can confirm cleanup. | Remote recovery waits until the hard deadline after normal completion, a cleanup flag or delete acknowledgement is reported as absence, or a stale fence can request cleanup for a newer lease. |

## Build order and exit gates

1. **Research and contracts.** Review current Vast marketplace, bidding, pricing, creation, monitoring, and destruction APIs. Write this plan, SDD, TDD, adoption contract, and checkpoint policy. Exit: every property has an acceptance case and every unresolved provider behavior is identified.
2. **Research routing.** Implement request/evidence schemas and `route` responses. Add exact-identity and provenance checks before adding paid operations. Exit: minimal context enters a research workflow; missing requirements cannot become invented numbers.
3. **Market and cost planning.** Record the sourced owner network tiers and provider unit evidence, normalize live responses, include all verification states/rental types, calculate exact-allocation phase/transfer/storage envelopes, rank eligible candidates, and implement finite sequential bid planning. Exit: unsupported units/month divisors and unknown costs cannot pass; fake-provider contract tests and ranking metamorphisms pass.
4. **Lease lifecycle.** Add provider client, durable journal/locking, ambiguous-create reconciliation, independent deadline supervisor, bounded installation/probe, destroy verification, and restart recovery. Exit: failure injection leaves no falsely completed lease and no duplicate create.
5. **Adopter and release.** Apply a non-destructive continuity overlay, run its preflight/validation, document import/CLI usage from a fresh clone, and run the acceptance suite in the required CI job named `gates`. Convert the scheduled snapshot workflow to an artifact or checked PR instead of direct default-branch push. Create a GitHub PR, attach it to the task, enable auto-merge, and check the merged revision. Exit: green candidate checks, observed PR-only enforcement, and a release checkpoint referencing the actual revision. Auto-merge configuration is not proof that merge occurred.
6. **Independent challenge.** Dispatch a fresh Luna with only the task, repository reference, owner limits, and configured credential access. The agent must discover sources and use the shipped router. Exit: real inference and verified destruction, or a truthful failed/blocked challenge report.

Prepare the portable controller/harness, manifests, report collector and acceptance probe before the challenge rents capacity. Measure GPU-host engine/loopback performance separately from each actual Tailscale client and checker run. Required GPU-specific work stays inside the paid envelope. Retained caches and parallel races are later release gates after sequential accounting/recovery passes; each requires its own property coverage and concrete owner limits. The researched decisions and open provider conventions are in [cost-and-benchmark-plan.md](cost-and-benchmark-plan.md).

## Ownership and independence

The architecture owner controls requirement/property changes and reviews the gate implementation. Builders work from public contracts. A separate evaluator owns private holdout cases and scores traces without modifying code to suit a failure mid-run. Root coordination records agreed changes and actual completion.

[VBR-0001 / issue #1](https://github.com/Pukujan/vastai-gpu-broker/issues/1) is the canonical task. Preserve the target's existing domain entry points while adding the continuity contract; do not import a source module's full task/checkpoint ledger into this target.

Open-Jev has already been named during design, so its model identity is not an unseen-model holdout. Its fresh-agent research and lifecycle challenge remains meaningful when the prompt contains no solved recipe. Additional private cases and mutations can test general behavior. Published fixture tests must not be described as hidden.

## Acceptance boundary

The initial module is a local trusted executable. Structural evidence checks make missing research enforceable; they cannot prove an arbitrary claim is scientifically true or prevent a credential holder from directly calling Vast outside the module. The design must state those limits rather than claim that documentation or a CLI is an unbypassable authority.

Likewise, a local supervisor bounds normal operation and retries cleanup; it cannot guarantee a provider-side spending cutoff during total controller/network failure. The module must preserve unresolved cleanup and report this honestly. These limitations do not excuse absent recovery or routine teardown.
